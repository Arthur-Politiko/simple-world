# Roadmap: живая деревня

**Статус:** активный план. Этапы 0–5 завершены для локального MVP. Typecheck, 34 теста, production build и HTTP smoke-test API памяти проходят. Визуальный осмотр Wiki-панели остаётся рекомендованной ручной QA-проверкой, но не блокирует этап. Следующий основной этап — 6: вертикальный срез с реальной моделью (перед ним нужно согласовать провайдера и бюджет).  
**Среда:** сначала локально, серверное размещение позже.  
**Принцип:** небольшие завершённые шаги с проверкой и сохранением состояния.

## 1. Правила работы

1. За один рабочий заход брать один небольшой шаг или подэтап.
2. Перед началом читать `CONCEPT.md`, `ROADMAP.md` и `STATUS.md`.
3. Не считать этап завершённым без проверки критериев готовности.
4. После каждого шага обновлять `STATUS.md`:
   - что изменено;
   - какие проверки выполнены;
   - что не работает или не проверено;
   - ближайший следующий шаг.
5. Значимые решения фиксировать в `docs/DECISIONS.md`.
6. Не подключать платный LLM API без согласования провайдера и бюджета.
7. Сначала делать рабочий вертикальный срез, затем расширять мир.
8. Не усложнять архитектуру ради будущей MMO.

**Важно:** один этап roadmap может занимать несколько сессий. При остановке нужно оставлять воспроизводимое состояние, а не только объяснение в чате.

## 2. Общая последовательность

```text
Документация
    ↓
Минимальный локальный проект
    ↓
Время, действия и сохранение
    ↓
Автономная деревня
    ↓
Внешнее давление и распространение сведений
    ↓
Память и протокол рефлексии
    ↓
Реальная модель на двух персонажах
    ↓
Забывание и изменение ядра
    ↓
Проверка гипотезы и расширение
    ↓
Подготовка к серверу
```

Ключевая контрольная точка — **два NPC проходят полный цикл «событие → рефлексия → память → изменившееся решение»**. До этого не следует вкладываться в большой мир и сложный интерфейс.

## Этап 6. Вертикальный срез с реальной моделью

**Цель:** проверить основную гипотезу на двух персонажах до расширения системы.

### Перед началом согласовать

- Провайдера и модель.
- Способ хранения ключа.
- Допустимый бюджет эксперимента.
- Лимиты запросов и контекста.
- Какие данные передаются внешнему провайдеру.

### Задачи

- [ ] Подключить реальный LLM-адаптер; по умолчанию оставить тестовый режим.
- [ ] Создать два различающихся ядра персонажей.
- [ ] Реализовать сборку релевантного контекста.
- [ ] Добавить выбор намерения из допустимых действий.
- [ ] Добавить рефлексию после значимой сцены.
- [ ] Ограничить параллельность, повторы и время ожидания.
- [ ] Учесть использование токенов и стоимость при известных тарифах.
- [ ] Обработать сбои и невалидные ответы без повреждения мира.
- [ ] Показать цепочку от события до нового решения.
- [ ] Добавить минимальное взаимодействие игрока: диалог и один материальный поступок.

### Критерии готовности

- Одно событие получает различный, согласованный с ядром смысл у двух NPC.
- Хотя бы одно изменение памяти влияет на последующее решение.
- Сервер отклоняет невозможные действия модели.
- Бюджет соблюдается; число повторных запросов ограничено.
- При ошибке API состояние остаётся корректным.
- Человек может объяснить поведение по сохранённой причинной цепочке.

### Контрольная точка

**Решить, подтверждается ли идея.**

Если поведение непоследовательно, сначала исправить контекст, промпты и протокол памяти. Не компенсировать проблему увеличением числа NPC.

### Критерии готовности

- Мир переживает перезапуск сервера без повреждения.
- Секреты недоступны браузеру и не попадают в репозиторий.
- Бэкап восстанавливается в проверенный рабочий мир.
- Расходы ограничены.
- Характеристики сервера выбраны по измерениям, а не только предварительной оценке.

---

## 3. Что не делать до проверки гипотезы

- Не строить MMO.
- Не добавлять большой процедурный мир.
- Не начинать с десятков модельных NPC.
- Не отправлять всю wiki в каждый запрос.
- Не внедрять микросервисы и распределённые очереди без необходимости.
- Не создавать сложную графику вместо инструментов наблюдения.
- Не генерировать драму только ради заполнения памяти.
- Не обещать психологическую последовательность на основании одного удачного диалога.

## 4. Формат завершения каждой сессии

В `STATUS.md` оставлять:

```markdown
# Состояние проекта

## Текущий этап
Номер этапа и конкретный подэтап.

## Сделано
Только реально выполненное.

## Изменённые файлы
Пути и краткое назначение.

## Проверки
Команды, результаты, ручные проверки.
Отдельно — что не проверено.

## Запуск
Актуальные команды и адрес приложения.
Если запуска ещё нет — прямо указать это.

## Проблемы и ограничения
Ошибки, незавершённые части, принятые компромиссы.

## Следующий шаг
Одна конкретная задача с критерием готовности.

## Требуется решение пользователя
Только вопросы, действительно блокирующие ближайший шаг.
```

## 5. Ближайший шаг

**Следующий этап реализации — этап 6: вертикальный срез с реальной моделью на двух персонажах.** До подключения API отдельно согласовать провайдера, модель, хранение ключа, передаваемые данные и лимит бюджета. Реальный API не запускать без согласования.

Визуальная проверка Wiki-панели остаётся рекомендованной ручной QA-задачей, но не блокирует локальный этап 5.
